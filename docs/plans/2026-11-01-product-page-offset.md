# BE08 상품 페이지 offset 경계 수정

기준 main `cb9023c4104692a586c33b156c18622b2fee9eca`, 작업 codex/product-page-offset.
상품 목록의 지원 범위를 넘는 정수 offset만 다룬다. 가격/도수·명시 태그의 S01 증가분과 분리한
기존 결함이며 다른 API와 공통 PageCriteria의 정규화/계산 정책은 변경하지 않는다.

## 기준·원인과 선택

제품 수정 전에 현재 PageCriteria의 실제 Java 클래스에서 다음을 확인했다.

| page / 정규화된 size | 기존 int offset | 같은 입력의 long offset |
|---|---:|---:|
| 2,147,483,647 / 100 | -200 | 214,748,364,600 |
| 42,949,674 / 100 | 4 | 4,294,967,300 |

`(page - 1) * size`가 int 안에서 계산되기 때문이다. 음수만 검사하면 두 번째 양수 래핑을
놓친다. 임의의 작은 페이지 상한을 도입하거나 SQL에서 다른 페이지로 보정하는 대안 대신,
상품 서비스에서 long으로 먼저 계산하고 0..Integer.MAX_VALUE 범위를 확인한 뒤 검증된 int를
DAO에 전달한다. 기존 0/음수 입력의 기본값과 size100 clamp는 그대로 사용한다.

조정자는 제품 수정 전에 현재 cb9023c의 불변 jar3fbb…·전용 MySQL8.4의 여덟 조건을 확인했다.
미지원 네 조건의 계약 위반 4/4 중 HTTP 500은 2/4, 잘못된 페이지의 HTTP 200은 2/4였다.
지원 범위 안의 네 조건은 200이었다. H10의 이전 기준과 구분하고 Java 산술값을 실제 HTTP 결과로 대신하지 않는다.
조건과 원값은 [정확성 검증](../measurements/2026-11-01-product-page-offset.md)에 보존한다.
로컬 도구 실행 실패나 테스트 개수도 제품 실패/성능의 분모가 아니다.

## 검증 계획

- 음수 래핑·양수 래핑·size100의 첫 범위 초과 페이지가 DAO를 호출하지 않고400 BAD_REQUEST인지 확인한다.
- 직전 허용 페이지·Integer.MAX_VALUE/size1과 기존 0/음수·크기 clamp·정상 페이지를 유지한다.
- 기존 Product7/PageResponse·필터/정렬·현재 MySQL 동작과 실행 문서를 유지한다.
- check.sh의 Java17·Python·패키징 후 불변 jar로 같은 HTTP 조건을 재측정하고 전체 폐기 smoke를 통과한다.

수정 전 새 MockMvc/fake DAO 회귀13조건 중 미지원 네 조건의400 기대만 실패한 것을 확인한 뒤
상품 서비스에 long 계산·범위 검사·검증한 int 전달을 구현했다. 최종 check.sh의 Java 17 Maven 133개·
Python 안전 게이트 28개·패키징·저장소 검사가 통과했다. 실행 OpenAPI/정적 계약의 지원 범위와
필수 HTTP의 네 조건400·정규화 동등성을 추가했다.

최종 불변 jar SHA-256: `ddd3ab6f70f2cb2b7d0b296ac85a1acd4f2f68934733babefe9df930211c9a65`.
같은 jar의 실제 여덟 조건 재측정은 [200,200,400,400,400,200,400,200]으로 통과했다. 지원 범위
밖 네 조건의 계약 위반은 4/4→0/4, 그중 HTTP 500은 2/4→0/4, 잘못된 페이지의 HTTP 200은 2/4→0/4였다.
지원 범위 안 네 조건의 200은 유지했다. 같은 jar·전용 MySQL의 full HTTP smoke 13범주도 통과해
기존 필터·세션·주문/rollback·삭제 이력·특성·취향·찜·기본 목록·실행 문서를 유지했다.
서버 오류와 잘못된200이 잘못된 요청의400으로 분류되는 정확성 수정이며, 전체 HTTP 오류율이나
사용자 장애율·응답 속도 개선으로 표현하지 않는다.
