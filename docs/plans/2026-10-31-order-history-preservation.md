# BE02 상품·회원 삭제 후 주문 이력 보존

기준은 main `56a76d147229f31e492ca9d7fd4e339ae1c1d357`이며 BE01 스냅샷을 포함한다.
기존 fk_order_detail_product와 fk_order_user의 ON DELETE CASCADE는 상품 삭제 때 상세를,
회원 삭제 때 주문을 함께 지운다. 금액 스냅샷만으로 행 소실을 막을 수 없으므로 삭제 경계를 분리한다.

## 선택과 책임

- 상품·회원은 기존대로 물리 삭제하고 주문 FK를 nullable/SET NULL로 바꾼다. 상품/계정을
  soft-delete하면 모든 탐색/로그인/검색 쿼리에 상태 조건이 필요하고 계정 자격정보/이름을
  계속 보관하게 된다. 이번에는 구매 이력과 활성 참조의 생명주기를 FK에서 분리한다.
- 상품 snapshot name/type/img·가격·수량·합계·header totalPrice/priceBasis는 유지한다.
  productId는 Integer nullable이며 0/가짜 ID로 바꾸지 않는다. 신규 주문은 양수 ID만 받는다.
- 삭제 회원의 주문 userId는 null이다. 이름/비밀번호를 새 snapshot으로 복사하지 않는다.
  삭제 API는 user FOR UPDATE→order_table 자유 입력 정리→계정 삭제를 한 트랜잭션에서 실행해
  새 주문이 정리/삭제 사이에 들어오지 않게 한다. 후기/스탬프의 기존 회원 종속 삭제는 유지한다.
- null 소유자 주문은 관리자만 조회하며 같은 문자열 ID로 재가입해도 과거 주문을 연결하지 않는다.
  응답 null과 화면의 삭제 표시/상품 링크 비활성화 계약을 Frontend에 전달했다. UI 구현은 그 레포 소유다.
- BE03 기존 세션 재조회·권한 회수·재가입 세션 인증은 별도이며 이번 결과로 완료 처리하지 않는다.

## 데이터 전환

[002 SQL](../migrations/002-order-history-preservation.sql)은 001 필드 조회로 선행 스키마를 확인하고
두 FK를 SET NULL로 교체한다. 기존 주문/상세/총액은 변경하지 않고 신규 초기 시드도 같은 FK를 사용한다.
[전환 안내](../ORDER-HISTORY-PRESERVATION.md)에 FK 이름/대상 검사, nullable·개수/합계 보존,
쓰기 중단·백업/복원, 네 DDL의 암시 커밋과 중간 실패/재실행 시 상태 확인 절차를 기록했다.
실행 시 foreign_key_checks를 끄거나 기존 DB에 초기화 SQL을 다시 적용하지 않는다.

첫 MySQL 8.4 전환 검증에서는 한 ALTER에서 이전 FK와 동일한 이름을 재사용해
ERROR 1826(Duplicate foreign key constraint name)이 발생했다. 이 시도를 성공으로 처리하지
않고 old FK 제거와 nullable/새 history FK 추가를 분리했다. 초기 스키마도 같은 새 이름을 사용한다.
MySQL 공식 문서에서 같은 ALTER의 FK add/drop은 INPLACE만 지원하고 COPY는 지원하지 않음을
확인해 동일 문장 재사용에 의존하지 않았다. 실제 실패의 상세 실행 알고리즘 자체는 확정하지 않으며
수정 SQL의 실제 전환을 다시 검증했다. 기존 주문 3개·상세 4개·총액 59,100원을 보존했고
history FK 두 개의 SET NULL을 확인했다. 중간 FK 누락 상태에서는 쓰기를 재개하지 않는다.

## 검증·측정

단위 경계는 응답 productId/userId가 null로 직렬화되는지, 상품 표시/금액이 남는지,
null 소유자를 일반 회원이 읽을 수 없고 관리자는 읽는지, 계정 메모 정리가 삭제보다 먼저인지다.
기존 주문/가격·트랜잭션 테스트도 유지한다.

필수 backend-ci의 안전 게이트가 있는 폐기 MySQL/실제 jar HTTP에 삭제·재가입 경로를 추가했다.
새 fixture 관리자만 폐기 DB에서 승격해 실제 관리자 API를 실행하며 기존 관리자/사용자 DB를
변경하지 않는다. 새 테스트 상품/회원/주문으로 상품 삭제→회원 삭제 후 스냅샷/페이지 보존,
의도된 참조 null과 메모 제거, 삭제 세션/재가입 계정 403·과거 목록 0을 확인한다.

수정 전후 실제 DB/HTTP 정확성은 조정자가 전용 환경에서 재현한다. 동일 초기 시드의 A/B
상품으로 A×2, B×3, A×1+B×2의 세 주문(66,000/217,800/178,200원)을 생성한다. 관리자 API로
상품 A를 삭제한 뒤 같은 구매자를 삭제하는 순차 흐름이다. 주문 존재·상세 행/상품 표현·단가·수량·
합계·header 총액을 보존 조건으로 삼고 의도된 참조/메모 null은 위반에서 제외한다. 같은 세 주문을
두 단계로 관찰하므로 독립 표본 여섯 건으로 합산하지 않는다.

기준 코드의 실제 HTTP/MySQL 결과는 상품 A 삭제 뒤 상세 4→2개, 상세 보존 위반 2/3건이다.
그 다음 구매자 삭제 뒤 신규 주문 3→0개로 주문 유실 3/3건이다. BE01은 상품 삭제 후 header
총액 자체는 남으므로 총액 하나만 비교하면 상세 소실을 놓친다.

최종 불변 jar(SHA-256 `12f68b4eae1f152a54b83c968bf86231d498ed716ae4b0488161040a36c8715a`)의
동일 순차 흐름은 상세 4→4개·위반 0/3건·null 상품 참조 2개, 이어 회원 삭제 뒤 주문 3→3개·
유실 0/3건이다. 금액 66,000/217,800/178,200원·상품 스냅샷을 유지하고 소유자/메모를 null로
바꿨다. 관리자 단건 조회·동일 ID 재가입 후 목록 0/단건 403도 확인했다.

[삭제 정확성 기록](../measurements/2026-10-31-order-history-preservation.md)에 같은 입력/초기 DB·
기준 커밋·원값·재현 코드/명령·DDL 실패 수정과 한계를 기록했다. Java 17 단위 검증 21개·Python 도구 18개와
패키징·저장소/공백 검증을 통과했고 실제 MySQL/HTTP 결과를 확인했다. 표준 CI smoke·PR 최신 head
필수 CI/Codex 리뷰·병합·main CI는 조정자의 별도 게이트다. 응답 성능·운영 장애율 성과로 변환하지 않는다.

## README 후보와 후속

실제 삭제/FK/전환 근거가 확보돼 BE-CS04를 가격 단독에서 가격·참조 삭제의 업무 이력 보존으로
보강했다. 이는 같은 주문 이력의 수명 경계이므로 새 슬롯으로 늘리지 않는다. 페이지 조립·인증·
입력 정규화 사례는 유지하고 정확히 네 개다. 이전 가격 실험과 이번 삭제 실험은 서로 다른
기준 커밋/변경이므로 측정 조건과 분모를 구분한다.

이미 과거 CASCADE로 삭제된 행은 복원하지 않는다. 직접 SQL 계정 삭제는 서비스의 자유 입력
정리를 거치지 않으므로 운영 삭제 경로로 사용하지 않는다. 전체 장애 주입/동시성/재시도와
세션 회수는 BE06/C04·BE03에 남긴다. PG·배송·모바일 구현은 추가하지 않는다.
