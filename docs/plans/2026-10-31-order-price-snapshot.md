# BE01 주문 시점 가격 보존

기준 커밋은 `a563c3693ea10452ced7c3c3eff4275badac3439`다. 기존 주문 조회 SQL은
`t_product.price * t_order_detail.quantity`로 계산해 상품 가격 변경이 과거 금액을 바꾼다.
이번 목적은 새 주문의 상품 표현/단가/라인 합계/총액을 서버에서 확정하고 기존 응답 필드를
유지하는 것이다. 상품·회원 삭제 CASCADE 보존(BE02), 세션 회수(BE03), 결제 PG는 포함하지 않는다.

## 선택과 구현

- 상세에 상품명/주종/이미지·단가/라인 합계, 주문에 총액과 가격 근거를 저장한다. 이후 목록/단건
  조회가 현재 상품 JOIN을 사용하지 않으며 기존 상세 일괄 조회와 페이지 경계를 유지한다.
- 서비스는 새로 만든 정규화 상세에 서버 상품 값을 채운다. SELECT FOR UPDATE로 상품 가격을
  잠금 조회하고 합계를 검사한 뒤 주문수를 갱신해 상품 변경과의 경계를 만든다. 행별 상세 저장 대신 배치 INSERT를 유지한다.
- 정수 합계/수량 오버플로를 거부하며 중간 쓰기 예외는 기존 Spring 트랜잭션으로 롤백한다.
- 과거 실제 단가는 복구할 수 없으므로 현재 값을 몰래 과거 가격으로 채우지 않는다. 전환 시점
  현재 값으로 고정한 값은 `LEGACY_ESTIMATE`, 새 주문은 `ORDER_SNAPSHOT`으로 구분한다.
  상세가 모두 사라진 과거 주문은 총액을 null로 남긴다.
- 기존 필드 이름/자료형은 유지하고 `totalPrice`, `priceBasis`를 추가했다. 마이그레이션은 자동
  실행하지 않으며 백업·쓰기 중단·strict mode·범위 사전 검사 후 1회 수행한다. MySQL DDL의
  암시 커밋과 재실행/복구 절차는 ORDER-PRICE-SNAPSHOT.md에 기록했다.

대안으로 현재 상품 가격을 계속 JOIN하는 방법은 과거 주문 불변 요구를 충족하지 않는다.
단가만 저장하면 상품명/표시 정보가 변경되어 과거 주문 맥락도 달라지므로 표시 스냅샷을 함께
저장했다. 계산된 라인/주문 합계를 저장하는 대신 매번 합산할 수도 있지만, 이번에는 서버가 확정한
금액을 명시적으로 보존하며 테스트로 단가×수량 및 라인 합계와의 일치를 확인한다.

## 검증 상태

수정 전 서비스 스냅샷 회귀는 1개 시나리오에서 기대 단가 1000에 대해 저장 필드가 없어 0으로
관측되어 실패했다. 이는 가짜 DAO를 사용하는 서비스 계약 결과이며 실제 HTTP/DB 가격 변경
오류율이나 서비스 성능 측정이 아니다. 같은 회귀는 수정 뒤 통과했다.

Java 단위 검증·패키징과 저장소/공백 검사를 통과했다. 기존 Python 도구 검증은 기본 sandbox의
ps/loopback 제한 때문에 실패했으며 권한이 있는 임시 프로세스·소켓 환경에서 재실행해 통과했다.
이 실행 환경 제한을 앱 오류 개선 수치로 사용하지 않는다.

필수 backend-ci의 폐기 DB HTTP smoke에 다음 검증을 추가했다.

1. 주문 상세 단가/합계·주문 totalPrice/priceBasis 확인.
2. 같은 폐기 DB 상품의 가격·이름 변경이 실제 반영됐는지 확인.
3. 같은 주문 단건/목록 응답이 변경 전과 완전히 일치하는지 확인.
4. 상품 값을 finally에서 복원한 뒤 기존 쓰기 후 실패 rollback과 세션 검증을 계속한다.

직접 SQL 변경 전에도 기존 loopback *_ci DB·컨테이너 포트·실행 marker 검사를 다시 통과해야 한다.
표시 이름은 UTF-8 hex로 전달해 SQL 문자 삽입을 막고 비밀번호는 프로세스 인자에 넣지 않는다.

### 최종 패키지 HTTP·전환 검증

조정자가 같은 초기 시드의 별도 폐기 MySQL 8.4와 기준/변경 jar에서 같은 세 주문을
생성하고 두 상품 단가를 각각 1,000원 올렸다. 최종 변경 jar는 빌드 뒤 불변 파일로 복사했으며
SHA-256은 `cdbd64ff44b42045ff5239a4cbbb598d6891efe3010302993e06c5c8e81a207f`다.

| 주문 입력 | 생성 금액 | 기준: 가격 변경 후 | 기준 차이 | 최종 변경: 가격 변경 후 | 최종 차이 |
|---|---|---|---|---|---|
| A×2 | 66,000원 | 68,000원 | +2,000원 | 66,000원 | 0원 |
| B×3 | 217,800원 | 220,800원 | +3,000원 | 217,800원 | 0원 |
| A×1+B×2 | 178,200원 | 181,200원 | +3,000원 | 178,200원 | 0원 |

A는 33,000원, B는 72,600원인 동일 시드 상품이다. 금액 불변 위반은 **3/3→0/3**,
이 시나리오의 오류율 차이는 **100%p 감소**다. 신규 단건/목록 DTO가 가격 변경 전후 일치하고
헤더 총액과 상세 합계도 일치했다. 응답 시간/처리량·실사용자 장애율 성과가 아니다.

이전 스키마 전환은 주문 6개·상세 8개를 보존했고 LEGACY_ESTIMATE 표시와 헤더/라인
합계 일치를 확인했다. 전체 파일 재실행은 중복 컬럼 오류로 중단되고 행 수/총액은 추가 변화가
없었다. 자동 재실행 가능한 멱등 마이그레이션이라고 주장하지 않는다.

실행 중 target jar가 재빌드되어 NoClassDefFoundError가 난 최초 시도는 무효 처리했다.
그 실패를 제품 결함 수치로 사용하지 않고, 별도 복사·SHA 확인한 최종 jar의 재측정만 채택했다.
[정확성 측정 기록](../measurements/2026-10-31-order-price-invariance.md)에 입력·코드/명령·
원값·측정 경계·재현 조건·한계를 남겼다. 구현과 로컬 DB/단위 검증은 완료했으며 PR 최신 head의
필수 CI·Codex 리뷰·병합·main CI 확인은 조정자가 별도로 수행한다.

## README 후보 비교

현재 네 사례 중 로컬 실행기 소유권 사례와 비교한다. 주문 금액 불변/과거 자료의 추정 표시와
비파괴 전환은 핵심 업무 데이터의 시간 경계를 직접 다뤄 DB/거래 포트폴리오 우선 기준과 맞는다.
실제 DB 가격 변경 및 전환 근거가 확보되어 기존 로컬 실행기 사례 하나를 가격 보존 사례로
교체했다. 실제 업무 영향·원인 규명·잠금/마이그레이션 대안·원값 비교가 더 직접적인 근거다.
페이지 조립·인증 전환·입력 정규화 사례는 별도 문제이므로 유지해 대표 사례는 네 개다.

## 남은 경계

BE02의 상품/회원 삭제 이력, 모든 쓰기 단계 장애·동시/중복 주문, 과거 이미 삭제된 상세 복구는
완료하지 않았다. Frontend의 priceBasis 표시도 별도 소유 작업으로 남는다. 기존 개발 DB는
임의 초기화/전환하지 않았으며 실제 결제·배송도 구현하지 않았다.
