# BE03 현재 계정·권한과 세션 정합성

기준 소스는 `0a3ddeec04600b94f57d3a77da53f8d507c7f68a`다. 기존 Guard는 로그인 때 저장한
SessionUser만 확인해 계정 삭제/권한 변경 뒤에도 같은 snapshot을 반환한다. 같은 문자열 ID로
재가입하면 이전 cookie가 새 계정 데이터에도 연결될 수 있다. 외부 사용자가 없는 로컬 프로젝트의
실제 HTTP/DB로 이를 재현하고 같은 조건의 변경 결과를 비교한다.

## 구현 결정

- 보호 요청마다 DB의 id+auth_epoch로 현재 계정을 확인하고 최신 역할/표시 데이터를 반환한다.
  캐시 snapshot의 역할은 권한 근거로 사용하지 않는다. 계정/자격이 사라지면 401, 현재 권한이
  부족하면 403이다. DB 실패에는 권한을 허용하거나 로그아웃으로 바꾸지 않는다.
- 계정 생성별 UUID로 삭제→같은 ID 재생성의 ABA 문제를 구분한다. 단순 id 존재 확인만으로는
  삭제 중 조회되지 않은 기존 세션을 막을 수 없다. 공개 응답에 epoch/hash를 추가하지 않는다.
- 비밀번호 변경은 epoch를 회전하고 프로필/역할 수정은 유지한다. 일반 정보 수정은 세션을
  재발급하지 않는다. 관리자 본인 비밀번호만 잠금 안의 변경 전 epoch와 관측 세션이 같을 때
  해당 수정이 실제 만든 epoch로 갱신하며 다른 기존 세션은 거부한다.
- Guard는 세션 표시 snapshot을 다시 쓰지 않고, DB 조회 후 현재 신원을 다시 확인한다.
  로그인/조건부 갱신/정리를 동기화해 새 로그인이나 로그아웃을 늦은 조회가 덮어쓰지 않게 한다.
- 생략한 관리자 수정 필드는 잠금 조회 후 최신 행에서 해결한다. 같은 비밀번호의 구형 해시
  전환은 epoch를 유지하고 hash+epoch CAS와 최신 행 재검증으로 동시 reset 덮어쓰기를 막는다.

상세 경계·비용·수동 003 전환은 [세션 계약](../SESSION-AUTHORITY.md)을 따른다. 데이터베이스
기존 값·사용자 볼륨은 임의 변경하지 않고 조정자 전용 폐기 환경에서만 검증한다.

## 기준 실제 HTTP 결과

같은 MySQL 8.4·JDK 17·별도 폐기 DB와 기준 불변 jar에서 서로 다른 다음 경계를 재현했다.
각 시나리오 표본은 1회이며 서로 다른 사건을 하나의 서비스 오류율로 합산하지 않는다.

| 경계 | 기준 관측 | 원치 않은 결과 n/N |
|---|---|---|
| ADMIN→USER 후 구세션 | 관리자 API 200, auth/me.role은 ADMIN | 1/1 |
| 회원 삭제 후 기존 세션 | auth/me 200 | 1/1 |
| 삭제 중 조회하지 않은 세션→동일 ID 재가입 | 구세션 profile 200, 새 로그인도 200 | 구세션 허용 1/1 |
| 비밀번호 변경 후 구세션 | auth/me 200, 구 비밀번호 로그인은 401/새 비밀번호 200 | 구세션 허용 1/1 |
| 이름/스탬프 변경 | auth/me는 두 값 모두 이전 값 | stale 표시 1/1 |

구 비밀번호 로그인 차단과 새 로그인 성공은 기존에도 되는 positive 경계이며 이번에 새로
구현한 성과로 바꾸지 않는다. dormant cookie는 삭제 직후 조회한 세션과 분리해 단순 세션
제거만으로 같은 ID 재가입 문제를 해결했다고 오인하지 않게 했다.

## 로컬 구현 검증과 후속 실측

Java 17 단위 38개·패키징, Python 도구 19개·저장소/공백·스모크 구문 검증을 통과했다.
단위 경계에는 최신 권한/표시, 삭제/재가입/비밀번호 회수, epoch 없는 구세션, DB 실패 보존,
조회 중 계정 전환/로그아웃, nonce 비공개, 생략 필드 보존·구형 hash CAS 경합을 포함한다.
가짜 DAO의 경합 재현을 실제 DB 동시성/전체 원자성 성과로 기록하지 않는다.

최종 패키지 SHA-256은 `b4c0351e9f6fba1dab654f0b0f84c6c69c2f444aed5615e4320b3f4c09141f07`다.
빌드 뒤 조정자가 별도 불변 파일로 복사해 같은 실제 HTTP 다섯 경계와 표준 CI smoke를 재검증했다.
조정자가 수행한 003 전환은 회원 6·주문 3·상세 4개, 기존 사용자 필드 바이트 동일을 보존했고
epoch 6/6 distinct·NULL 0·NOT NULL을 확인했다. SQL SHA-256은
`881c80bb2231b9d672b63e78b04bb901a40b827615232d6ca69502bb0da6d400`이다.

첫 변경 artifact에서는 다섯 HTTP 경계를 통과했지만 후속 소스 검토에서 본인 수정의 사후 재조회가
다른 관리자의 새 epoch를 구세션에 채택할 수 있음을 발견했다. 이를 최종 검증으로 사용하지 않고
잠금 안의 불변 UserUpdateResult와 변경 전 버전 검사로 수정했다. 변경 전 회전·커밋 뒤 회전·일반
정보 수정의 epoch 미채택과 컨트롤러의 사후 재조회 금지를 단위 인터리빙으로 검증했다.

최종 artifact에서 각 경계의 위반은 각각 1/1→0/1이다. 강등은 403/현재 USER, 삭제·재가입 구쿠키·
비밀번호 변경 구세션은 401, 이름/스탬프는 최신 값이며 새 로그인·민감 필드 비공개를 유지했다.
기준도 CI 기본 default0900 새 스키마·원본 시드·불변 기준 jar로 재실행해 같은 원값을 확인했다.
최종 전후의 collation은 같고 표준 smoke도 CI 기본 collation의 새 폐기 DB에서 통과했다. 첫 smoke 시도는 실험자가 별도
unicode_ci DB를 만들어 fixture SQL과 충돌한 ERROR 1267로 실패했으며 성공으로 처리하지 않았다.
정확한 원값·전환·재현·중간 검토/실패 경계는 [측정 기록](../measurements/2026-11-01-session-authority.md)에 남긴다.
PR 최신 head CI·Codex 리뷰·병합·main CI는 별도 게이트이며 아직 이 문서에서 완료 처리하지 않는다.

## README 비교·남은 범위

기존 BE-CS02 해시 점진 전환은 가짜 DAO/해시 규칙에 주로 근거했다. 이번 BE03은 실제 권한과
계정 인스턴스의 수명·401/403·DB 장애·갱신 경합을 실제 전후 HTTP/DB와 버전 경계로 설명한다.
세션이 새 계정에 붙는 업무 영향을 직접 재현하고 잠금/세션 상태·대안 비용을 함께 설명하므로
더 강한 근거로 이 인증 사례 한 개를 교체했다. 나머지 세 개는 유지해 총 네 개이며 같은 인증
주제를 다섯 번째로 늘리지 않는다. [선정 등록부](../case-study-register.md)에 비교 근거를 남겼다.

전체 요청을 계정 삭제와 원자적으로 묶거나 이미 인증된 in-flight 작업을 취소하는 기능,
분산 세션 저장소·모든 동시성/부하 검증은 완료하지 않았다. DB 읽기/잠금 비용의 응답 성능도
아직 측정하지 않았다. PG·모바일·AWS·신규 인증 방식으로 범위를 확장하지 않는다.
