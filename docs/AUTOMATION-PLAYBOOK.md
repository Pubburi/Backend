# 세 영역 에이전트와 지속 개선

현재 채팅의 2시간 예약 하나를 유지한다. 조정자와 Backend·Frontend·Recommendation
전담 하위 에이전트가 협업하며 새 사용자 채팅이나 영역별 중복 예약은 만들지 않는다.
기한은 2027-02-05까지이고 2027-02-06 00:00 Asia/Seoul부터 새 구현·커밋·병합을 중단한다.
AWS 연결 전 로컬 개발, 모바일 별도 담당, 챗봇·실제 결제·배송 제외 범위는 유지한다.

## 역할과 소유권

| 역할 | 책임 |
|---|---|
| 조정자 | 최신 기획·Git/PR/CI·활성 작업 확인, API/ERD 계약과 선행 조건 조정, 저장소 소유권·위임 기록, 통합 검증·머지 게이트·Notion·최종 인계 |
| Backend 에이전트 | Java17·Spring·확정 PostgreSQL/JPA/Flyway 전환, 이관 전 MySQL 기준 보존·정합성·트랜잭션·인증/권한·공통 API·쿼리·동시성 |
| Frontend 에이전트 | Vue 유지와 승인된 React 전환, 라우팅·상태·세션/API 연동·실제 브라우저·접근성·자산·렌더링 |
| Recommendation 에이전트 | Python 3.12·FastAPI·데이터 출처/누락·특성·추천/이유·콜드스타트·fallback·학습/평가·재현성 |

코드·설계·테스트·상세 계획·문서·PR은 해당 역할의 레포가 소유한다. Backend는 업무 API/DB/인증과
[검색 연동 계획](SEARCH-PLAN.md), Frontend는 UI/상태/브라우저와 프론트 문서,
Recommendation은 [데이터·모델·평가 계획](https://github.com/Pubburi/Recommendation/blob/main/docs/DATA-AND-MODEL-PLAN.md)이 정본이다.
조정은 공통 기획/계약 참조로 하고 다른 역할의 상세 문서나 구현을 한 레포에 모으지 않는다.

매 실행은 세 전담 에이전트를 재사용하거나 생성해 각 영역의 실제 작업을 위임한다.
동시에 활동할 수 있는 수는 조정자 포함 네 명으로 제한한다. 같은 현재 채팅에 속한
하위 에이전트 간 협업 도구 통신을 사용하고, 사용자의 다른 채팅이나 외부 사람에게는 메시지를 보내지 않는다.
하위 에이전트는 허용된 레포·파일·명령 범위와 계약을 먼저 확인한다.

조정자가 저장소별 lease를 원자적으로 획득하고 위임한 에이전트·파일·Git 작업 소유자를
ignored 기록에 남긴다. 레포마다 한 명의 쓰기 소유자를 둔다. 조정자와 작업자가 같은
파일이나 index/branch를 동시에 바꾸지 않는다. 공통 정책·계약 파일을 조정자가 수정하면
작업자에게 그 파일을 제외한다. 작업자는 자기 레포 밖의 파일을 수정하지 않는다.

다른 살아 있는 작업이 소유한 checkout은 보존한다. 해당 영역은 읽기 전용 확인이나
대기로 제한하고 독립적인 다른 영역을 계속한다. 잠금 시간만으로 소유권을 빼앗거나
kill/stash/reset하지 않는다. 하위 에이전트를 쓰는 것이 기존 잠금이나 PR 게이트의 예외는 아니다.

단위·정적 검사처럼 독립적인 검증은 병렬 진행할 수 있다. 세 서버·공유 DB·포트·모델 파일을
사용하는 통합 검증과 성능 측정은 조정자가 실행 자원을 예약해 충돌 없이 진행한다.
성능 비교 중 다른 빌드·부하를 섞지 않는다. 각 영역이 변경·근거·실패·미실행·차단과
실제 head/PR/CI를 인계한 뒤 조정자가 전체 계약을 확인한다. Notion은 조정자가 한 번만 갱신한다.

## README의 대표 문제 해결 네 개

각 레포의 최종 README에는 채용 담당자가 기술적 판단과 구현을 평가할 수 있는
**대표 문제 해결 사례를 정확히 네 개** 둔다. 순서는 아래 여섯 항목으로 고정한다.

1. **문제:** 실제 영향·발생 조건. 관측한 결함과 예방적 설계 제약을 구분한다.
2. **원인:** 데이터·상태·요청·프로세스 경계를 좁혀 간 증거와 현재 소스의 동작.
3. **해결:** 선택한 방식과 실제 구현. 단순 변경 내역이나 도구 목록으로 대체하지 않는다.
4. **결과:** 실제로 확인한 동작과 한계. 성능을 다룬다면 동일 조건의 변경 전후 실측만 쓴다.
5. **대체안/회고:** 비교한 방법, 선택 이유, 비용과 남은 제약.
6. **코드:** 실제 핵심 처리 흐름을 읽을 수 있는 충분한 발췌를 기본으로 펼치고 현재 유효한 소스 링크를 연결한다.

없는 과거 장애·개인 기여·학습 결과·성능 수치를 만들지 않는다. 가짜 stub, 생략을 위한
코드, 미구현 기능과 수집하지 않은 데이터를 성과로 쓰지 않는다. 같은 bootstrap·CI 문제를
여러 사례로 쪼개 숫자를 맞추지 않는다. 아직 네 개의 근거가 없는 영역은 실제 확보 수와
부족분을 `docs/case-study-register.md`와 기획에 기록하고, 구현·재현·평가 과제로 확보한다.
부족한 슬롯을 README의 가짜 사례나 빈 자리표시자로 채우지 않는다.

매 실행마다 기존 사례와 이번 작업의 새 후보를 비교한다. 무조건 교체하지 않고
채용 담당자에게 더 설득력 있는 실제 문제 해결을 발견했을 때만 교체한다.
새 실사례가 생기면 실제 영향, 비동기/상태/데이터 경계의 난도, 원인 규명 근거,
대안과 선택 이유, 확인 가능한 구현 기여와 결과를 기존 네 개와 비교한다.
더 설득력 있는 사례 하나를 확보하면 해당 항목 하나부터 교체한다. 네 개가 새로 모일
때까지 기다리지 않고, 한 실행의 교체 수를 제한하지 않는다. 비교 근거 없이 최신성·코드량·
테스트 총수·임의 점수로 교체하지 않는다. 강한 근거가 없는 나머지 사례는 보존한다.
선정·교체 이유, 소스/PR, 관측 조건과 검증·측정의 실제 상태는 register와 작업 계획에 남긴다.

README에는 회귀 검증 증빙·테스트 수/목록·CI 집계 설명을 넣지 않는다. 실제 검증은
계속 수행하고 작업 계획·PR·CI에 기록한다. 테스트 통과 개수·audit 항목 감소·CI 시간은
서비스 성능 수치가 아니다. 성능 미측정인 정확성 사례는 기능 결과와 측정 상태를 구분한다.
Backend·Recommendation은 스크린샷을 요구하지 않고 Frontend는 검증된 실제 완성 화면만 사용한다.

세 README의 **관련 프로젝트와 개발자** 섹션, 레포/담당 표, 개발자/기여 표,
기획·협업·소스 출처 모음, 모바일 담당 소개와 그 목차/앵커는 재추가하지 않는다.
기존 출처 문서 자체는 보존한다. 필요한 실제 코드 링크와 실행 안내를 이 금지와 혼동하지 않는다.

## 기획 완료 후에도 계속하는 개선

실사용자가 없고 행동 데이터도 쌓이지 않는 조건에서 개발한다. 원천 선택·적법한 범위의 수집·
정제·특성 설계·모델 학습/비교·평가·채택/미채택은 조정자와 담당 에이전트가 공식 출처,
데이터 감사와 재현 실험에 근거해 결정하고 실행한다. 통상적인 개발 선택을 매번 사용자에게
되묻지 않는다. 사용자 모집·미래 로그 축적·외부 평가자 확보를 필수 선행 조건으로 두지 않는다.
Recommendation 정본의 카탈로그 학습·고정 시나리오/상품군 분리 기준을 따른다.
시연 입력과 합성 프로필은 기능 시험 조건이며 실제 사람의 선호·인기·CTR/구매 전환 성과가 아니다.
실제 원천의 권리/필드 부족은 기록하며 허용된 대안으로 진행한다. 기존 비용·계정 권한·외부 연락
경계는 유지한다. 계획 수정만으로 수집·모델 학습·평가를 완료 처리하지 않는다.

각 영역은 진행 중 작업·리뷰 결함·승인된 필수 항목을 우선한다. 자신의 실행 가능한
기획 작업이 끝났거나 막혔다면 독립적인 기존 기능의 오류·최적화 기회를 탐색한다.
전체 기획의 체크가 끝난 뒤에도 기한까지 세 영역의 결함 수정·신뢰성·성능·추천 품질을
계속 개선한다. 기능 완료를 이유로 단순 감시만 하거나 개발을 조기 종료하지 않는다.

- Backend: 주문/가격/이력 보존, 권한·세션, 롤백·중복/동시 요청, 인덱스·조회 수·지연과 오류 복구.
- Frontend: 실제 고객/관리자 흐름, 요청 경쟁·상태 복원·오류 표시, 세션, 접근성·자산·네트워크·렌더링 병목.
- Recommendation: 누락·이상치·데이터 누수, 필수 조건 위반·제외 피드백·콜드스타트·다양성·이유 정합성, 학습/평가 재현성과 응답 지연.

발견 항목에는 재현 조건·관측 증거·영향·우선순위·완료 기준·담당·선행 조건을 붙여
기존 항목과 중복 없이 Notion과 작업 계획에 등록한다. 성능 과제는 변경 전에 지표·단위·
기준 커밋·입력/부하/환경·캐시·워밍업·반복·제외 기준을 정해 실제 기준값을 측정한다.
변경 뒤 같은 조건의 원값·표본 수·중앙값/분포·차이·개선율·편차·실패와 한계를 기록한다.
0 기준값으로 비율을 만들지 않고 잡음 수준의 차이를 개선으로 확정하지 않는다.
추천 품질도 데이터·분리·기준선·지표·한계를 명시하고 합성 로그를 실제 선호 성과로 쓰지 않는다.

검증 가능한 작은 변경을 구현하고 기존 필수 CI·최신 head Codex 리뷰·관련 수동 검증을
통과해 미해결 지적이 없을 때만 PR을 Squash merge한다. 원래 리뷰 스레드 답글과 native 해결,
main CI 확인·ff-only 동기화·병합 브랜치 원격/로컬 삭제를 계속 수행한다.

근거 없는 리팩터링·빈 커밋·사례 채우기·신규 상용 기능 확장은 하지 않는다.
실제 수정할 근거가 없으면 상태를 보존하고 반복 알림 없이 다음 실행에 이어간다.
계정·권한·비용·외부 메시지의 실제 승인 경계, AWS 미연결과 기한 종료는 그대로 적용한다.
